Plataforma Educativa en tu servidor
Despliegue de prueba con Docker, PostgreSQL y HTTPS
Proyecto: Plataforma Educativa IoT
Versión 1.0 · Noviembre 2026
Resumen. Esta guía explica, desde cero y sin dar nada por sentado, cómo llevar la plataforma que tienes en C:\Plataforma Educativa hasta el dominio sistematizacion.itsoeh.edu.mx. Se explica qué es cada pieza (DNS, SSH, Docker, PostgreSQL, HTTPS), qué comandos escribir, qué respuesta esperar y qué hacer cuando algo no sale como se esperaba. Al final tendrás la aplicación accesible por HTTPS con tres usuarios de prueba listos para iniciar sesión.

1. Qué vamos a hacer exactamente

Imagina que tu aplicación es una tienda que hoy está funcionando solo en tu casa (en tu equipo Windows). Quieres mudarla a un local propio en Internet para que cualquiera pueda visitarla escribiendo sistematizacion.itsoeh.edu.mx. Para eso necesitamos cuatro cosas:

  • El local: tu servidor Linux (al que entras por SSH).
  • La señalización: el DNS, que es el que dice «ese nombre de dominio corresponde a esta IP».
  • La mudanza: copiar los archivos del proyecto al servidor.
  • La puerta y el letrero: un «reverse proxy» que recibe a los visitantes por HTTPS y los reparte entre la página web y la API.

En el servidor se levantarán cuatro contenedores (piezas de software aisladas, como cajas independientes dentro de una misma máquina):

ContenedorQué esPara qué sirve
dbPostgreSQL 16Guarda usuarios, dispositivos y eventos de forma permanente.
backendFastAPI (Python)Es la lógica de la aplicación: login, roles, dispositivos, catálogo.
frontendReact + ViteEs la página web que ve el usuario en el navegador.
proxyCaddyEntrega el certificado HTTPS y dirige el tráfico al frontend o al backend.
Nota. Caddy es el único componente que no estaba en el stack original. Lo añadimos porque es la forma más sencilla de obtener HTTPS automático (certificado de Let's Encrypt) sin configurar manualmente certificados ni renovarlos.

3. Comprobación previa: lo que necesitas tener

Antes de escribir un solo comando, confirma que tienes esto a la mano:

  • El dominio sistematizacion.itsoeh.edu.mx (fíjate: lleva ación, no solo ci: es sistematizacion, no sistematizcion).
  • Acceso al DNS del dominio (por si hay que crear o corregir el registro A).
  • La IP pública del servidor y tus datos de acceso SSH (usuario y contraseña o clave).
  • Que tu usuario pueda usar sudo (o que entres directamente como root).
  • La carpeta C:\Plataforma Educativa en tu Windows con el proyecto completo.
  • Un poco de paciencia: la primera vez, descargar imágenes y generar el certificado puede tardar varios minutos.
Advertencia. No hagas esto en un servidor de producción con datos reales todavía. Es una prueba. Las contraseñas que vienen por defecto son de prueba y se explican en la sección 13.

4. Fase 1 — Comprobar que el dominio apunta a tu servidor

Esta es la comprobación más importante. Si el nombre de dominio no apunta a tu servidor, Caddy no podrá obtener el certificado HTTPS y la página no cargará. Lo verificamos desde tu Windows y, después, desde el propio servidor.

4.1 Desde tu Windows

Abre PowerShell (botón de Inicio → escribe powershell → Enter) y escribe:

nslookup sistematizacion.itsoeh.edu.mx

Debes ver una sección llamada Respuestas no autoritativas: con una o varias direcciones Dirección: seguidas de una IP. Esa IP debe ser la IP pública de tu servidor.

4.2 Desde el servidor

Conéctate por SSH (sustituye usuario y IP_DEL_SERVIDOR):

ssh usuario@IP_DEL_SERVIDOR
dig +short sistematizacion.itsoeh.edu.mx

Si dig no está instalado, funciona igual con nslookup sistematizacion.itsoeh.edu.mx. La orden debe devolver directamente una IP. Si no devuelve nada, el registro aún no existe o no ha terminado de propagarse.

Consejo. Si no tienes dig, instálalo con sudo apt install -y dnsutils y vuelve a intentarlo.

4.3 Si el dominio no resuelve

Entra al panel donde administras el DNS (puede ser el de tu proveedor de dominio, Cloudflare, etc.) y crea o corrige un registro de tipo A:

CampoValor
TipoA
Nombre / Hostsistematizacion (o @ si el panel usa el dominio completo)
Valor / DestinoLa IP pública de tu servidor
TTL3600 (una hora) o el valor por defecto

Después de guardar, los cambios de DNS pueden tardar desde unos minutos hasta unas horas en propagarse. Vuelve a ejecutar dig +short hasta que devuelva la IP correcta antes de continuar con la Fase 6.

5. Fase 2 — Abrir los puertos 80 y 443

Caddy necesita el puerto 80 para hablar con Let's Encrypt y demostrar que el dominio es tuyo; después usa el puerto 443 para servir la web cifrada. Si estos puertos están cerrados, el certificado nunca se emitirá.

5.1 Si el servidor usa UFW (lo habitual en Ubuntu)

sudo ufw allow 80/tcp
sudo ufw allow 443/tcp
sudo ufw status

En la salida de sudo ufw status deben aparecer dos líneas con ALLOW IN para 80 y 443.

5.2 Si usa firewalld (habitual en CentOS/RHEL/Fedora)

sudo firewall-cmd --permanent --add-service=http
sudo firewall-cmd --permanent --add-service=https
sudo firewall-cmd --reload
sudo firewall-cmd --list-services

5.3 Si tu proveedor tiene firewall externo

Muchos proveedores (AWS, Azure, Google Cloud, OVH, DigitalOcean) tienen además un firewall en su panel de control. Entra al panel y asegúrate de permitir el tráfico entrante TCP en los puertos 80 y 443 desde 0.0.0.0/0 (cualquier origen). Si solo abres el firewall del sistema pero no el del proveedor, seguirá sin funcionar.

Advertencia. Si ya tienes Apache o Nginx escuchando en el puerto 80 o 443, Caddy no podrá usarlos. Comprueba con sudo ss -tulpen | grep -E ':80|:443'. Si aparece otro programa, hay que pararlo o cambiar el plan (por ejemplo, usar el proxy que ya tengas).

6. Fase 3 — Instalar Docker en el servidor

Si todavía no lo tienes, ejecuta estos comandos uno por uno. Son los pasos oficiales para Ubuntu/Debian. Pulsa Enter después de cada línea y espera a que termine antes de pasar a la siguiente. 

sudo apt update && sudo apt install -y ca-certificates curl gnupg
sudo install -m 0755 -d /etc/apt/keyrings
curl -fsSL https://download.docker.com/linux/ubuntu/gpg | sudo gpg --dearmor -o /etc/apt/keyrings/docker.gpg
echo "deb [arch=$(dpkg --print-architecture) signed-by=/etc/apt/keyrings/docker.gpg] https://download.docker.com/linux/ubuntu $(. /etc/os-release && echo $VERSION_CODENAME) stable" | sudo tee /etc/apt/sources.list.d/docker.list >/dev/null
sudo apt update
sudo apt install -y docker-ce docker-ce-cli containerd.io docker-buildx-plugin docker-compose-plugin
sudo usermod -aG docker $USER
Nota. El último comando añade tu usuario al grupo docker para que no tengas que escribir sudo delante de cada orden. Para que aplique, cierra la sesión SSH y vuelve a entrar.

Comprueba que quedó bien instalado:

docker --version
docker compose version

Ambos comandos deben mostrar un número de versión. Si docker compose version dice que no existe el comando, instala también el plugin: sudo apt install -y docker-compose-plugin.

7. Fase 4 — Subir el proyecto al servidor

Ahora vamos a copiar los archivos desde tu Windows al servidor. Te doy dos formas: la rápida (recomendada) y la visual, por si te resulta más cómoda.

7.1 Opción A: con PowerShell (recomendada)

Paso A1. En tu Windows, abre PowerShell dentro de la carpeta del proyecto. Si no sabes cómo, abre PowerShell y escribe: 

cd "C:\Plataforma Educativa"

Paso A2. Crea un archivo comprimido sin las carpetas pesadas:

tar -czf plataforma-deploy.tar.gz --exclude=node_modules --exclude=.venv --exclude=.run --exclude=__pycache__ --exclude=.git -C "C:\Plataforma Educativa" .

Qué hace este comando: -czf crea un .tar.gz; cada --exclude evita meter archivos que no hacen falta y que ocupan mucho (node_modules se reinstalará dentro de Docker). Se creará el archivo plataforma-deploy.tar.gz en la misma carpeta.

Paso A3. Cópialo al servidor (sustituye usuario e IP):

scp plataforma-deploy.tar.gz usuario@IP_DEL_SERVIDOR:/tmp/

Te pedirá la contraseña del servidor y luego verás una barra de progreso.

Paso A4. En el servidor, descomprime y entra en la carpeta:

sudo mkdir -p /opt/plataforma-educativa
sudo tar -xzf /tmp/plataforma-deploy.tar.gz -C /opt/plataforma-educativa
sudo chown -R $USER:$USER /opt/plataforma-educativa
cd /opt/plataforma-educativa
ls

El último ls debe mostrar, entre otros, backend, frontend, infrastructure, .env.example, DEPLOY.md y CREDENCIALES_PRUEBAS.txt. Si no aparecen, el archivo se descomprimió en otro sitio: revisa que estés en /opt/plataforma-educativa con pwd.

7.2 Opción B: con WinSCP (más visual)

Si te resulta más fácil trabajar con ventanas: instala WinSCP, conéctate al servidor con tus datos SSH, crea la carpeta /opt/plataforma-educativa y arrastra hacia ella el contenido de C:\Plataforma Educativa (excepto .venv, node_modules y .run). Después entra por SSH y ejecuta el chown y el cd del paso A4.

8. Fase 5 — Crear y configurar el archivo .env

El archivo .env contiene los «secretos» y la configuración del despliegue. No está en el paquete que subiste (por seguridad), pero sí está el ejemplo. Lo creamos ahora.

8.1 Crear el archivo

cp .env.example .env
nano .env

nano es un editor de texto sencillo que viene en el servidor. Muévete con las flechas. Cuando termines de editar:

  • Guardar: Ctrl + O y después Enter.
  • Salir: Ctrl + X.

8.2 Qué debes revisar en el archivo

VariableQué haceQué hacer con ella
DOMAINEl dominio donde estará la appDéjala como viene: sistematizacion.itsoeh.edu.mx.
POSTGRES_DBNombre de la base de datosNo hace falta cambiarla.
POSTGRES_USERUsuario de la base de datosNo hace falta cambiarlo.
POSTGRES_PASSWORDContraseña de la base de datosCÁMBIALA OBLIGATORIAMENTE. Reemplaza CambiarEstaContraseña por otra.
SESSION_TTL_SECONDSDuración de la sesión (8 horas)Déjala como viene.
CORS_ALLOWED_ORIGINSQuién puede llamar a la API desde el navegadorYa apunta a tu dominio HTTPS.
VITE_API_BASE_URLDirección de la API que se compila dentro de la webYa apunta a https://sistematizacion.itsoeh.edu.mx/api/v1.
INITIAL_*_PASSWORDContraseñas de los tres usuarios de pruebaDéjalas para la prueba; cámbialas para uso real.

8.3 Generar una contraseña segura para PostgreSQL

Si quieres una contraseña buena sin inventarla, ejecuta antes en el servidor:

openssl rand -base64 24

Copia el resultado y pégalo como valor de POSTGRES_PASSWORD (sin comillas ni espacios).

Advertencia. El script de despliegue se negará a continuar si la contraseña sigue siendo CambiarEstaContraseña. Es una protección para que no te quede la contraseña por defecto. Tampoco subas nunca el archivo .env a GitHub ni lo compartas.

9. Fase 6 — Validar y levantar los servicios

9.1 Primero validamos el archivo de orquestación

docker compose --env-file .env -f infrastructure/compose/compose.prod.yaml config

Este comando no levanta nada: solo comprueba que el archivo esté bien escrito y que todas las variables existan. Si está correcto, verás en pantalla una descripción larga de los cuatro servicios. Si falta una variable, el comando lo dirá claramente.

9.2 Ahora sí, desplegamos

bash infrastructure/deploy.sh

Este script hace tres cosas en orden:

  1. Valida el compose (igual que el paso anterior).
  2. Construye las imágenes del backend y del frontend y levanta los cuatro contenedores.
  3. Muestra el estado final de los servicios.

La primera vez verás muchas líneas de descarga e instalación. Es normal que tarde entre 3 y 10 minutos.

Nota. El certificado de Let's Encrypt se genera en el primer arranque. Si el navegador muestra una página de error de certificado durante el primer minuto, espera un poco y recarga. Puedes seguir el proceso con: 
docker compose --env-file .env -f infrastructure/compose/compose.prod.yaml logs -f proxy
Para salir de los logs, pulsa Ctrl + C.

10. Fase 7 — Comprobar que todo funciona

Haz estas cuatro comprobaciones, en este orden.

10.1 La página principal responde

curl -I https://sistematizacion.itsoeh.edu.mx/

La primera línea debe decir HTTP/2 200 o HTTP/1.1 200 OK.

10.2 La API responde

curl -s https://sistematizacion.itsoeh.edu.mx/openapi.json | head -c 200

Debe mostrar texto que empieza con {"openapi": y el título de la API. Esa es la documentación automática de los endpoints.

10.3 El login funciona

curl -X POST https://sistematizacion.itsoeh.edu.mx/api/v1/auth/login \
  -H 'Content-Type: application/json' \
  -d '{"id":"admin","password":"dev-admin"}'

Debe devolver algo parecido a {"token":"..."}. Ese token es tu sesión.

10.4 Entrar desde el navegador

  1. Abre https://sistematizacion.itsoeh.edu.mx/.
  2. Inicia sesión con admin / dev-admin.
  3. Comprueba que ves el menú de administrador (con Usuarios, Dispositivos y Catálogo).
  4. Repite con docente / clave-docente y con estudiante / clave-estudiante. El menú debe ser más limitado.

Consejo. Si la página abre pero el login falla, abre también https://sistematizacion.itsoeh.edu.mx/docs. Ahí puedes probar los endpoints desde la propia documentación y ver el error exacto.

Lista de éxito:

  • El dominio abre por HTTPS con candado.
  • /openapi.json devuelve JSON.
  • Los tres usuarios inician sesión con su rol correcto.
  • Los cuatro contenedores aparecen como Up en docker compose ps.

11. Fase 8 — Uso diario: estado, logs, reinicio y actualización

Guarda estos comandos; son los que usarás normalmente. Ejecútalos siempre dentro de /opt/plataforma-educativa.

# Ver el estado de los cuatro contenedores
docker compose --env-file .env -f infrastructure/compose/compose.prod.yaml ps

# Ver logs en directo (Ctrl+C para salir)
docker compose --env-file .env -f infrastructure/compose/compose.prod.yaml logs -f backend
docker compose --env-file .env -f infrastructure/compose/compose.prod.yaml logs -f proxy

# Reiniciar solo la API
docker compose --env-file .env -f infrastructure/compose/compose.prod.yaml restart backend

# Parar todo SIN borrar la base de datos
docker compose --env-file .env -f infrastructure/compose/compose.prod.yaml down

# Volver a levantar tras haber copiado cambios al servidor
bash infrastructure/deploy.sh
Advertencia. El comando down -v sí borra el volumen de PostgreSQL, es decir, elimina todos los datos y hace que los usuarios de prueba se creen de nuevo al levantar. Úsalo solo si quieres empezar desde cero.

12. Solución de problemas frecuentes

Lo que vesCausa probableQué hacer
Caddy no genera certificado / el navegador dice «no es seguro». El DNS no apunta al servidor o el puerto 80 está cerrado. Ejecuta dig +short sistematizacion.itsoeh.edu.mx, abre el 80 y revisa logs -f proxy.
Error 502 en /api. El backend no arrancó; casi siempre falta una variable de entorno. Revisa logs -f backend. SESSION_TTL_SECONDS y POSTGRES_PASSWORD son obligatorias.
El script dice «cambia POSTGRES_PASSWORD». Sigues con el valor de ejemplo. Edita .env y pon una contraseña real con openssl rand -base64 24.
El login devuelve «Credenciales no válidas». Los usuarios iniciales solo se crean si la base está vacía, o la contraseña cambió. Si ya habías creado usuarios, usa los tuyos; para reiniciar la prueba, down -v y vuelve a desplegar.
El build falla al instalar dependencias de Python. El intérprete no tiene ruedas binarias disponibles. El Dockerfile ya usa python:3.13-slim, que es el verificado. Si lo cambiaste, vuelve a 3.13.
«address already in use» al levantar. Otro programa (Apache/Nginx) ocupa el 80 o el 443. Para el otro servicio con sudo systemctl stop apache2 o nginx y vuelve a desplegar.
La web carga pero las llamadas a la API son bloqueadas. Estás abriendo por IP en vez de por dominio y CORS no lo permite. Usa siempre el dominio, o añade el origen a CORS_ALLOWED_ORIGINS y reinicia el backend.

13. Seguridad: lo que debes cambiar antes de un uso real

  • Cambia las tres contraseñas de prueba (dev-admin, clave-docente, clave-estudiante) usando las variables INITIAL_*_PASSWORD de .env antes del primer arranque, o cámbialas desde la API.
  • No compartas ni subas .env: contiene la contraseña de PostgreSQL y las de los usuarios.
  • Las contraseñas nunca se guardan en claro: se almacenan con PBKDF2-HMAC-SHA256, 200.000 iteraciones y sal aleatoria por usuario.
  • Las sesiones duran 8 horas y se pueden cerrar con /api/v1/auth/logout.
  • Recuerda que es un despliegue de prueba: cuando pases a producción, revisa copias de seguridad de PostgreSQL y limita quién tiene acceso SSH.
